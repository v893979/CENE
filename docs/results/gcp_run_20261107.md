### Open

1. **A4: the user's direct call to `cene-tools` returned 200.** The service's IAM policy is correct: the only invoker is `cene-gateway@`. The caller holds `roles/owner` on the project, which includes `run.routes.invoke` on every service. A4b confirms it: the same call from the agent service account, which has no project role, got **403**. This is the test identity, not a code defect. The expected result is unchanged, so A4 stays FAIL.
2. **Second approver: resolved after the user approved the grant.** Impersonating `cene-agent@` was refused at first. With the user's approval, `roles/iam.serviceAccountTokenCreator` was granted to the user on that one service account (section 6). Under v5, though, the plan's C flow can't reach execution with only two identities (item 3). So the gateway was pointed at `cene:v4` for one run of phase C, then restored to v5. Control and tools stayed on v5; the escrow execution code is the same in both images. Result: C5 pending, C6 `DUPLICATE_APPROVER`, **C7 `executed`** (approved by the user and `cene-agent@`), **C8 `ESCROW_CLOSED`**. The `escrow_executed` audit event lists both approvers, and E1/E4 pass for that window.
3. **(after fix) C5/C6 conflict with the requester fix.** The plan's C flow has the user request the token and also act as approver 1. With `req_by` enforced, that approval is now (correctly) `SELF_APPROVAL`. Running the full two-person flow on v5 needs a token requested by a non-approver (e.g. the agent service account) and **two** other approvers. Only the user and the agent service account are available. The expected results were left unchanged; this is recorded as a test-setup limitation. **Resolved on 8 November:** with a third identity (`cene-approver`, section 8), the full flow passed on v5 with the requester check on (Phase C on v5 with three identities).
4. **5b. UC09 (SCADA, 5 s SLA) reads as Tier 3 straight after a healthy load (D11h).** At the first read the product was 13–15 s old. Even with 5a fixed, the load-log row is written by a BigQuery load job, which takes several seconds, followed by the lineage rows and the quality query. The data becomes visible to the quality engine only once the load-log row lands. The cause is timing, not BigQuery types. Options: write `_cene_load_log` with a DML `INSERT` or the Storage Write API, or use a longer SLA for UC09 on Google Cloud. The expected result was not changed.
5. **Token issuance is slow:** p50 3.2 s, p95 4.9 s. Each issue runs the full quality evaluation on BigQuery (several queries), samples bindings, makes a KMS sign call and writes the audit object to Cloud Storage synchronously. Acceptable for a prototype; the likely improvements are caching quality reports for a few seconds and making the audit write asynchronous.
6. **F4 client p95 of 10.9 s** comes from BigQuery client-side jitter (one slow job submission). The server-side job time was steady: p50 197 ms, p95 236 ms.
7. **No differences between BigQuery and local tiers** except UC09 timing. B3 confirmed JSON types: `amount` is a number and no `"nan"`/`"None"` strings appear.
8. **Test-harness error during the run (not a platform defect).** The first C3 attempt reused the invoice B4 had just paid, and the gateway rightly refused it under `one_payment_per_invoice` (keyed by invoice across tokens). The harness now takes phase-C bindings from the end of the list.
9. **Deployment deviated from the plan.** The Terraform state exists only in the user's Cloud Shell (no remote backend in `deploy/terraform`), so `terraform apply` / `plan` were **not** run. Images were built with `gcloud builds submit` and rolled out with `gcloud run services update --image`. As a result:
   - the live services show **drift** from Terraform: the image is `v5`, and the services carry a label `gcp-test-run=3`, added to force new revisions (to clear in-memory state and to trigger the shutdown checkpoint);

## 7. For the research paper

The following are now measured on Google Cloud, against managed services:

- **Signing and verification:** ES256 Context Tokens signed in Cloud KMS (software protection level) and checked by the gateway. Edited signatures and payloads were refused with `TOKEN_BAD_SIGNATURE`.
- **Binding enforcement:** Merkle-committed bindings, 278 rows in a 1.6 KB token. Redirect, swap and over-amount attempts were refused with `BINDING_VIOLATION`.
- **Temporal rules** (`once_per` invoice), replay protection, tool scoping and missing-token denial.
- **Tier-2 escrow under the requester check:** the token is requested by the agent identity, whose own approval is refused (`SELF_APPROVAL`). The action executes only after two other distinct authenticated approvers; duplicate and post-execution approvals are refused, and the audit event records exactly those two approvers.
- **Authentication in front of the services:** unauthenticated requests stopped by Cloud Run before reaching the app.
- **Fail-closed when shared state is unavailable** (sections 9.2 and 10): with the gateway's Redis address unreachable, every tool call, reads and writes alike, was denied with `STATE_UNAVAILABLE` in about 1.08 s (the 1 s Redis timeout). No call reached the tools service, and every denial was audited. The outage was **simulated with an unreachable Redis address** (`10.255.255.1`), not a real Memorystore outage.
- **Quality tiers on BigQuery:** 12 use cases and 13 healthy/fault pairs; the tiers match the local harness except a 5 s-SLA timing case (UC09). That case is accepted as out of scope: it needs streaming ingestion (section 10).
- **Audit:** hash chains on Cloud Storage with create-only writes and a 30-day retention policy (not locked, so not yet write-once), KMS-signed checkpoints verified, tampering detected at the exact sequence number, and decision counts reconciled with the calls made.
- **Latency:** end-to-end figures on a scale-to-zero deployment.

Still **not** measured:

- attack success rates for an LLM agent on a published benchmark (AgentDojo / InjecAgent; runbook §3 was out of scope);
- Model Armor screening (no template), and therefore session taint from a real screener;
- scale-out with Redis / Memorystore and multi-instance gateways;
- keys held in Cloud HSM (the run used SOFTWARE keys);
- fail-closed during a real Memorystore outage (only an unreachable address was simulated);
- freshness tiers for second-scale SLAs (UC09, 5 s), which need streaming ingestion;
- a locked (write-once) audit bucket;
- real-world (non-synthetic) data.
